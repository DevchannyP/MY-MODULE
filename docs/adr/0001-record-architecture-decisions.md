# ADR 0001: 아키텍처 결정 기록 방식 채택

**날짜**: 2026-03-17
**상태**: 수락됨 (Accepted)
**결정자**: [확인 필요: 결정자 기재 필요]

## 맥락

소프트웨어 아키텍처 결정을 추적하지 않으면 나중에 "왜 이렇게 했지?"를 알 수 없다.
특히 Workflow OS처럼 Stage 기반으로 반복 실행하는 구조에서는 결정의 근거가 중요하다.

## 결정

- 모든 구조적 판단은 `docs/adr/` 아래에 ADR(Architecture Decision Record)을 작성한다.
- ADR 없이 구조 변경을 진행하지 않는다 (constraints.yaml C004).
- 파일명 형식: `NNNN-제목.md` (예: `0001-record-architecture-decisions.md`)
- 상태 값: `제안됨 | 수락됨 | 거부됨 | 대체됨 | 폐기됨`

## ADR 템플릿

```markdown
# ADR NNNN: [제목]

**날짜**: YYYY-MM-DD
**상태**: [상태]
**결정자**: [이름]

## 맥락
[왜 이 결정이 필요했는가?]

## 결정
[무엇을 결정했는가?]

## 결과
[이 결정의 영향은?]

## 대안
[검토했으나 채택하지 않은 대안들]
```

## 결과

- 모든 아키텍처 결정이 추적 가능해진다.
- 새 팀원이 결정 근거를 이해할 수 있다.
- Stage 재실행 시 이전 결정을 참조할 수 있다.

## 대안

- 없음 (ADR은 최소 오버헤드로 최대 추적성을 제공하는 표준 관행이다)
