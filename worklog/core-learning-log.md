# 코어 업그레이드 학습 로그

이 문서는 지금까지의 코어 업그레이드를 한 번에 이해하기 쉽게 다시 설명한다.

## 1. 전역 품질 게이트 정렬

### 왜 했나

한 교실에서 앞줄 학생만 검사하고 뒷줄 학생은 안 보면 공평하지 않다.
코드도 마찬가지다.

### 무엇을 했나

- lint 범위를 `task-management` 한 곳에서 저장소 전역으로 넓혔다.
- `domains + src + scripts`를 공통 기준으로 묶었다.

### 배운 점

좋은 기준은 "어느 파일이든 같은 규칙으로 검사한다"는 데서 시작한다.

## 2. 계약 드리프트 검증

### 왜 했나

문서와 코드가 다른 말을 하면 나중에 큰 충돌이 난다.

### 무엇을 했나

- capability / ui / openapi / events / interface를 비교하는 검증기를 넣었다.

### 배운 점

계약은 종이가 아니라, 자동으로 검사될 때 진짜 계약이 된다.

## 3. 타입 경계 기준선

### 왜 했나

입구와 출구가 어떤 모양인지 적어 두지 않으면 물건이 잘못 들어간다.

### 무엇을 했나

- 핵심 포트, 엔티티, 인터페이스에 JSDoc + `@ts-check` 기준을 넣었다.

### 배운 점

전체 TypeScript 전환 전에도 타입 안정성은 단계적으로 올릴 수 있다.

## 4. 운영 기준선

### 왜 했나

고장났을 때 어디를 봐야 하는지, 어떻게 되돌릴지를 모르면 운영이 불안하다.

### 무엇을 했나

- observability
- rollback
- feature flag

기준을 문서와 검증 명령으로 고정했다.

## 5. 공급망 기준선

### 왜 했나

내가 만든 결과물이 무엇으로 만들어졌는지 남겨야 나중에 믿을 수 있다.

### 무엇을 했나

- SBOM
- provenance evidence

기본 산출물을 만들었다.

## 6. authn/authz와 smoke 게이트

### 왜 했나

문이 잠기는지, 기본 길이 열리는지 따로 검사해야 한다.

### 무엇을 했나

- `test:authn-authz`
- `test:e2e-smoke`

를 독립 게이트로 만들었다.

## 7. Git 거버넌스와 release evidence

### 왜 했나

좋은 코어는 코드만 좋아서는 안 된다.
누가, 왜, 어떤 검증을 거쳐 바꿨는지도 남아야 한다.

### 무엇을 했나

- 브랜치 전략
- PR 기준
- 학습형 로그 템플릿
- release evidence 생성기

를 추가했다.

## 8. dependency scan 기준선

### 왜 했나

문 앞에 경비원이 없으면 누가 들어왔는지 모른다.
의존성도 마찬가지다.

### 무엇을 했나

- `scan:dependencies`를 placeholder 에서 실제 검증기로 바꿨다.
- lockfile 이 잠겨 있는지
- runtime dependency 가 새로 들어오지 않았는지
- integrity 와 license 가 있는지

를 자동으로 확인하게 했다.

### 배운 점

보안 검사는 꼭 인터넷과 거대한 도구가 있어야 시작되는 게 아니다.
먼저 "내 저장소 안에서 당장 증명할 수 있는 것"부터 고정하는 게 중요하다.

## 9. 온라인 advisory feed 전략

### 왜 했나

자물쇠를 잘 잠갔는지 보는 검사만으로는 부족하다.
밖에서 "이 자물쇠 모델은 오늘부터 위험해요"라는 뉴스가 나올 수 있다.

### 무엇을 했나

- 오프라인 baseline 과 온라인 advisory 를 두 층으로 나눴다.
- 어떤 경우에 `main`을 막을지 정했다.
- 예외를 허용할 때 꼭 적어야 할 항목도 정했다.

### 배운 점

보안 정책은 "도구 이름"보다 "언제 막고 언제 기록만 할지"가 먼저 정해져야 흔들리지 않는다.
