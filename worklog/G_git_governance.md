# Git 거버넌스 작업 로그

## 2026-03-19 - Core Platform - 브랜치 전략과 release evidence 기준선 추가

**날짜**: 2026-03-19  
**트랙**: CORE-OPERATIONS  
**실행자**: Codex (자동화)

## 1. 왜 이 작업을 했나

아주 쉽게 말하면, 지금까지는 "무엇을 만들지"는 점점 좋아졌지만
"어떻게 안전하게 저장하고 되돌리고 설명할지"에 대한 규칙은 약했다.

이건 공구는 좋은데 공구함 정리가 안 된 상태와 비슷하다.

## 2. 이전 상태의 문제

- 저장소에 첫 커밋도 없었다.
- 기본 브랜치 규칙이 없었다.
- PR 설명 기준이 없었다.
- release evidence를 남기는 자동 파일이 없었다.
- 학습용 로그를 어떤 형식으로 남길지 기준이 없었다.

## 3. 이번에 추가한 것

- ADR 0007
- Git 거버넌스 참조 문서
- Git 실행 가이드
- PR 템플릿
- commit 메시지 템플릿
- 학습형 로그 템플릿
- release evidence 생성 스크립트

## 4. 핵심 코드 읽기

### 파일

`scripts/generate_release_evidence.py`

### 이 코드가 하는 일

이 코드는 "지금 저장소 상태를 한 장의 영수증처럼 남기는 기계"다.

- 지금 브랜치가 무엇인지 읽고
- 현재 커밋이 무엇인지 읽고
- current-state에서 품질 상태를 읽고
- next-actions에서 다음 작업을 읽고
- 이 정보를 JSON 파일로 저장한다

### 왜 중요한가

나중에 다른 프로젝트와 연결할 때
"이 변경은 어떤 상태에서 만들어졌는가?"를 설명할 수 있어야 한다.

release evidence는 그 설명의 출발점이다.

## 5. 배운 점

- 좋은 형상관리는 git 명령 몇 개를 아는 것보다 "규칙을 저장소 안에 문서화"하는 게 더 중요하다.
- 코어 저장소는 코드만이 아니라 memory, ADR, worklog까지 같이 버전 관리해야 한다.

## 6. 다음 작업

- dependency scan 기준선 실동작화
- 실제 커밋/브랜치/PR까지 원격과 연결

## 7. 이번 턴에 실제로 한 git 행동

1. 로컬 작성자 이름과 이메일을 저장소에 설정했다.
2. 기본 브랜치를 `main`으로 바꿨다.
3. 현재 전체 저장소 상태를 root baseline commit으로 남겼다.
4. `chore/core-git-governance-activation` 작업 브랜치를 만들었다.
5. 이 브랜치에서 release evidence를 다시 생성해 실제 git 상태를 반영하도록 했다.
